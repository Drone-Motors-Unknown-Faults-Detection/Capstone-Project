## 1. 一句話與重點摘要

本專題研究：**當馬達出現訓練時沒見過的訊號型態，系統能否先標記未知、收集相似樣本，再經人員確認把它納入已知類別，同時保留可追查的實驗紀錄。**

Ancestor 提供學長的感測資料處理、CNN 分類與遷移學習、HDBSCAN 分群及馬氏距離未知偵測流程；Lineage 延續這些資料與研究問題，重寫健康冷啟動、逐類開放集分數、校準、候選新類更新、趨勢顯示與 Web 示範。公開演算法與學長成果均保留來源，Lineage 的貢獻主要是流程改造、實驗比較、系統整合與可重現性建置。[Ancestor 程式說明][a-readme]、[Lineage 核心][l-monitor]。

目前最能支持的結果與限制如下：

| 可以核對的結果 | 白話意義 | 不能推論的事 |
|---|---|---|
| 正式 exp6 在九工況、三個 seed、兩方法的 54 組結果中，Ledoit–Wolf 馬氏距離的健康接受率平均 94.6214%，未知召回率 100%；k-NN 為 94.5683% 與 100%。[正式彙總][r-exp6] | 在各工況各自建立健康基準後，現有故障配置與健康有很強的分離；兩方法差異很小。 | 這是健康／非健康二元任務，沒有證明九種故障配置都能分類，也沒有證明跨馬達泛化。 |
| 歷史深層特徵比較的 18 個模型，二元開集準確率由 95.0947% 升至 98.6447%，增加 3.55 個百分點。[歷史原始彙總][r-old-lw] | 更換整套拒絕規則後，這批既有資料的已知／未知判定較好。 | 同時改了逐類建模、共變異數估計、校準與 inlier 使用方式；不能把全部增益歸給收縮，也不是本次新盲測。 |
| 主線跨工況實驗與另存的跨馬達故障類型研究暴露了明顯失敗；後者 N5 已知分類約 25.74%、未知 AUROC 約 0.53。[研究結果][research-final] | 同工況能發現異常，與換馬達仍能辨識故障，是兩個難度不同的問題。 | 未合併研究不能寫成 main 已具備的功能；增加演算法數量也沒有自動解決資料與泛化問題。 |

最重要的界線是：**現有成果是一套離線研究與 CSV 回放展示系統。** 三顆馬達、同一批資料的重複切分及合成劇本，還不足以支持真實磨損生命週期、剩餘壽命（RUL）、現場每小時誤報率或已部署飛行監測的宣稱。Web 的「健康度」與研究用健康指數都是相對分數，沒有物理損壞百分比的標定。[回放來源][l-live]、[健康指數實作][l-health]。

## 2. 想解決什麼問題

一般分類器必須從已知選項挑一個答案。若只學過健康與幾種螺絲配置，遇到新型態訊號時，直接選最像的舊類別可能把未知故障掩蓋。專題因此把「有沒有超出已知範圍」放在「屬於哪一類」旁邊一起處理。

在這個專案中，「未知」是**相對於本次模型的已知集合**。健康冷啟動只知道 `8screws`，其餘配置都是未知；加入 `7screws` 後，該配置成為已知故障，仍然不是健康。另一些實驗預先知道健康與四種故障，保留另外五種作未知。不同設定的準確率不可直接混比。[冷啟動][l-exp1]、[多類比較][l-exp11]。

| 工作 | 系統回答的問題 | 目前的做法與界線 |
|---|---|---|
| 異常／開放集偵測 | 這筆訊號是否超出所有已知範圍？ | 距離除以校準門檻；最小正規化分數大於 1 判未知。這不是故障機理鑑定。 |
| 已知分類 | 若在範圍內，最接近哪個已知配置？ | 主線以最近的正規化類別分布決定；研究分支可另用共用分類器。 |
| 未知分群 | 被隔離的資料是否形成相似群？ | HDBSCAN 尋找密度群與噪聲；一群不保證就是一種真實病因。 |
| 新類更新 | 人員認可的新群，能否變成已知類？ | 主線確認後讀取該配置完整資料池並重擬合；這是有標籤、全資料池的示範更新。 |
| 趨勢監測 | 分數是逐漸改變，還是突然跳變？ | EWMA、CUSUM 顯示與劇本規則；尚無連續磨損資料驗證。 |

上述工作共用資料，但衡量方式不同。AUROC 衡量分數排序；未知召回率看固定門檻抓到多少未知；健康誤報率看多少健康被拒絕；多類準確率看類別是否答對；分群純度要用事後標籤核對。任何一個高分都不能代替其餘工作。

## 3. Ancestor 已經完成哪些基礎

### 3.1 學長研究與來源

Ancestor 保存沈品志的碩士研究程式及《利用深度學習輔助式學習替診斷無人機馬達未知故障檢測》論文 Markdown 轉錄，指導教授張淵仁，逢甲大學航太與系統工程學系，2025 年 6 月。本文以程式為實作依據；轉錄有錯字、表格省略及敘述不一致，未取得原始論文 PDF 核對，因此不把轉錄中的百分比當作本次重新驗證結果。[論文轉錄][a-thesis]。

Ancestor 的六步流程是：

1. 原始感測 CSV 清理與分窗。
2. 建立統計及頻域特徵，另產生 clean 特徵檔。
3. 訓練健康與四種已知配置的 CNN、ResNet、VGG 類模型，並做單階段／雙階段遷移。
4. 抽取模型中間層特徵，以 HDBSCAN 與馬氏距離觀察已知／未知群。
5. 隨機組合未知配置，再做批次偵測。
6. 把健康及九個故障配置合併，訓練十類模型。

已盤點到 128 份 notebook：Step3 有 45 份，Step4、Step5、Step6 各 27 份，另有 GPU 測試及 T1/T2/T3 健康指標各一份；數量表示檔案範圍，不表示本次已執行 128 次訓練。[固定版本目錄][a-tree]。

### 3.2 實際程式與容易誤讀的地方

Ancestor 的五種已知標籤為 `8/1/2/3/4screws`。代表性的 Step3 CNN 使用一維卷積、池化、全連接與 softmax；資料分成 80% 訓練及 20% 評估，但同一個 20% 也提供 EarlyStopping 的 validation。這不是另留一個完全未參與模型選擇的 final test。[Step3 Model01][a-step3]。

遷移程式載入舊 `.keras`，凍結約前半層，使用目標工況有標籤資料微調。Model10–18 對應 T2，Model19–27 對應 T3；部分 8000 RPM 的 OneStage／TwoStage 起點相同，不能把兩個檔名當作兩種獨立證據。這些深層模型與 Lineage 主線直接使用 105 維特徵的監測器是不同路徑。[Model10 OneStage][a-step10]、[Model13 TwoStage][a-step13]。

Step4／5 的代表程式先對已知深層特徵做 HDBSCAN inlier 篩選，再估計**合併已知類別的單一中心與經驗共變異數**，加 `1e-6 I` 後取偽逆。門檻取訓練距離第 95 百分位；測試批次重新分群，判定的是**群中心**到已知分布的距離。部分群名透過測試真實標籤的多數決命名，不能當成不需人員的病因識別。[Step4][a-step4]、[Step5][a-step5]。論文轉錄另寫平均距離加 1.96 倍標準差，與這個 notebook 不一致；本文不混用兩種門檻。

Step6 代表程式重新建立 CNN，使用十類資料訓練；它沒有保存「每次到達新群後，僅用當下樣本更新」的完整線上學習歷程。[Step6][a-step6]。T1/T2/T3 notebook 的 HI 是人工指定分段線性標籤加隨機噪聲，再用同批資料擬合與預測 MLP；沒有實測壽命標籤與獨立測試，不能作為已驗證退化曲線。[HI notebook][a-hi]。

因此，原始感測設計、105 維特徵、三種深層架構、遷移學習方向、HDBSCAN、馬氏距離及十類重訓練，均屬既有基礎。Lineage 的報告必須清楚承接，而不重新歸為自己的發明。

### 4.1 為什麼仍然叫馬氏距離改善

馬氏距離的形式仍是：

`d(x,c) = sqrt((x−μc)ᵀ Σc⁻¹ (x−μc))`

Ledoit–Wolf 改的是共變異數估計：將容易受有限樣本影響的樣本矩陣，朝縮放後的單位矩陣收縮，使逆矩陣較不容易放大小特徵值的估計誤差；這是 Olivier Ledoit 與 Michael Wolf 於 2004 年提出的公開方法。[原論文][paper-lw]。本專案再配合逐類中心與獨立 calibration，取 `min_c(d(x,c)/τc)` 作未知分數。[實作][l-maha]。

對高度相關的統計特徵，這是合理的改善動機；但「條件數改善」到「故障判定改善」之間還受到特徵、資料清理、類別結構與門檻影響。現有歷史比較一次改動多個因素，沒有提供單因素因果證據；跨馬達分布偏移也不會因共變異數可逆就自然消失。

## 5. 系統怎麼走完一次診斷與更新

### 5.1 資料與決策流程

```text
既有感測 CSV → 清理／分窗／105 維特徵 → 選定馬達與 RPM
                                          │
已知資料：train → fit scaler＋detector ─────┤
           cal → 每類 q95 門檻 ────────────┤
                                          ▼
                           回放一筆未用於當前 fit 的樣本
                                          │
                              最小正規化分數 ≤ 1？
                      ┌───────────────────┴──────────────────┐
                     是                                      否
           健康或已知故障＋類別                      未知（不等於已確診病因）
                      │                                      │
                      └──→ 趨勢／幾何／事件紀錄 ←────────────┤
                                                             │score > 2
                                                             ▼
                                                      隔離區累積樣本
                                                             │
                                               HDBSCAN：成群？／噪聲？
                                                   │無群      │候選群
                                             繼續收集         ▼
                                                   人員確認／資料真值模擬
                                                    ┌────────┴─────────┐
                                                 已知邊界群           新配置
                                               清除該群、不更新       │
                                                                     ▼
                                                   讀取該配置完整池、重擬合
                                                   更新門檻／射線／快照
                                                                     │
                                                            回到監測（故障仍在）
```

這張圖描述主線實作，不是硬體部署圖。健康資料的 train／cal／holdout 在模型中分開；未知配置回放時使用完整池。新類確認後才建立該配置的切分，因此發現階段可能已看過日後 holdout 裡的樣本，後續「學會後準確率」不能當成嚴格未接觸的線上新類測試。[資料與循環抽樣][l-data]、[確認流程][l-exp2]。

### 5.2 一個例子

選 T1／8000 RPM，先以 `8screws` 建健康基準。操作者切換為 `7screws` 回放；若分數超過 1，系統顯示未知；若超過 2，該筆進隔離區。隔離區有足夠密度群後出現候選。操作者按「操作員確認 → 納入並重訓練」，程式用這個配置的完整標記池重擬合。之後同樣的訊號可能被辨識成已知 `7screws`，分數也可能降低。

這個變化表示模型已認識此配置，**不表示螺絲恢復、馬達修好或設備更安全**。候選純度、配置名與「其實是已知群」判斷來自資料標籤，並非密度分群自行推得病因。批次 exp2 會自動執行確認，Web 則留下按鈕操作節點。[exp2][l-exp2]、[Web 控制][l-server]。

### 5.3 各層責任與失敗處理

`core/` 負責資料、分數、校準、監測器、幾何與紀錄；`experiments/` 固定問題、切分、指標及輸出；`web/` 呼叫同一實驗／session，處理控制與畫面。exp1、exp3、exp4、健康逐窗監測有共享的逐步事件路徑，批次與串流不應各寫一套判定。[實驗頁編排][l-webexps]。

找不到資料、缺健康類或維度錯誤時應停止並回報；監測器 fit 失敗後會標成未完成，後續使用會拋錯。HDBSCAN 沒有成群時持續累積，不能假裝已發現。Web tick 發生錯誤會暫停串流；重擬合／換資料集失敗會顯示事件。這些保護有助於展示故障可見，但目前沒有完整模型更新交易回滾、長期模型登錄與真實人員標註系統，不能據此宣稱現場可用。[監測器][l-monitor]、[伺服器][l-server]。

## 6. 資料代表什麼，怎麼分配才有意義

### 6.1 馬達、轉速、配置與特徵

資料沿用 Ancestor 的實驗來源。T1、T2、T3 是三顆不同馬達；既有文件把 T1 描述為較新、T2／T3 描述為使用過的馬達，但缺少可查的個體序號、完整使用時數與退化真值。因此，本報告把它們當成不同個體，不把 T1→T2→T3 當成同一顆馬達的生命週期。[馬達身分說明][motor-guide]、[來源限制][research-provenance]。

| 項目 | 實際設定與可支持範圍 |
|---|---|
| 工況 | 三顆馬達 × 6000／8000／11000 rpm，共九個馬達／轉速條件；掃描器只列出實際存在的檔案，不保證下載後自然齊全。 |
| 健康配置 | `8screws`。這是本資料集的健康標記，不代表所有設備的健康定義。 |
| 其他配置 | `1screws` 至 `7screws`、`3_14screws`、`4_146screws`。目錄亦可能使用單數 `1screw`。配置名稱來自實驗標記，不自動等於九種不同物理故障原因。 |
| 原始訊號 | 三軸加速度、電流、溫差；Ancestor 程式以 10 kHz、每窗 10000 點設定計算。程式常數不能代替感測器校正與採集紀錄。 |
| 105 維特徵 | 電流與溫差各 15 個統計量；三軸振動各 15 個統計量及 10 個倍頻峰值，共 `15 + 3×25 + 15 = 105`。包括 RMS、均值、峰度、標準差、偏度、峰對峰值與 FFT 1X–10X。 |
| 主線輸入 | `data/Step-*/myfeature/{Motor}/{RPM}/{Config}/*_Group_feature_data_clean.csv`，一列是一個特徵窗，資料目錄不進 Git。研究分支另有 75 維等表示，不是主線預設。 |

來源：[Ancestor 訊號切窗][a-preprocess]、[特徵程式][a-features]、[Lineage 載入器][l-data]。不能把一列直接換算成連續一秒的真實運轉：舊程式先對每個通道各自移除 IQR 離群點，再串接、切窗；不同通道可能移除不同時間點，後續還會裁到相同最小列數。這能產生同尺寸特徵，卻不能證明各通道仍同步。[前處理][a-preprocess]、[特徵對齊][a-features]。

Lineage 的正式資料轉換器可讀既有 clean 特徵，也能從封裝的 Step-2 通道窗重算 105 維；目前遇到通道窗數或長度不同會拒絕，不再默默裁短。它同時檢查 ZIP 路徑穿越、重複成員與 symlink 等風險。但「尺寸一致」仍不等於「原始時間一致」，也不保證新版嚴格入口能重建所有舊資料產物。[正式資料轉換器][l-formal]。

### 6.2 三種資料角色與兩套主要切分

| 角色 | 用途 | 不應做的事 |
|---|---|---|
| train | 擬合 RobustScaler、類別中心、共變異數、鄰居或分類器。 | 看未知配置或最終測試結果來選特徵與參數。 |
| calibration | 用已知資料的距離分布設定拒絕門檻；主線逐類 q95。 | 把未知測試召回調到最好，或與 train 混用卻仍稱獨立校準。 |
| holdout／test | 最後評估已知接受、分類與未知拒絕。 | 評估後繼續選模型，卻稱為尚未曝光的最終盲測。 |
| discovery／update | 模擬尚未認識的資料到達、聚群及確認後更新。 | 使用未來完整資料池卻稱只靠已到達樣本學習。 |

主線 exp6 的正式比較，在每個工況內把健康配置隨機分成 60% train、20% calibration、餘下 holdout；九種其他配置全部作未知評估，不參與初始 fit／calibration。三個 seed 改變切分，沒有增加馬達數。這回答「已看過這顆馬達這個轉速的健康資料，能否抓到其他配置」，不回答「完全沒看過另一顆馬達能否診斷」。[切分程式][l-data]、[正式實驗][l-formal-exp]。

| 0 | T1：5935 | T2：6007 | T3：9294（已知 5604／未知 3690） |

### 7.2 主線 exp1–5：從異常偵測走到工況限制

#### exp1：健康冷啟動

- **研究問題：**只用健康資料，能否拒絕未看過的配置？
- **為什麼做：**故障資料不足時，先建立健康基準比先列完所有故障類更可行。
- **使用資料：**T1／8000 rpm，健康 313 窗、其他九配置合計 2736 窗，seed 42。
- **分配：**健康 187 train、62 calibration、64 holdout；其他配置只評估。
- **方法：**train-only RobustScaler、LW 健康共變異數、校準 q95，正規化距離大於 1 判未知。
- **成功標準：**未找到事前固定的跨馬達數值通過線；q95 是門檻設定，不是實測誤報保證。
- **結果與限制：**九配置的宏平均偵測率與 AUROC 都為 1；健康誤報 7／64＝10.94%。它表示故障分布容易離開這個健康基準，同時約每九個健康窗就有一個被拒絕，不能只報「100%」。[程式][l-exp1]、[實際 summary][r-exp1]。

#### exp2：新配置發現、操作員確認與量尺擴張

- **研究問題：**陌生樣本能否形成候選，確認後成為可辨認類別？
- **為什麼做：**一直顯示「未知」不足以累積診斷知識。
- **使用資料：**T1／8000 rpm，seed 42；從健康開始，依序注入 7、6、5、4、3、2、1、3_14、4_146 配置。
- **分配：**健康先作 60／20／20；未知從完整配置池循環抽樣。確認後讀該配置完整池重新切分、重擬合，不只使用已收集隔離樣本。
- **方法：**分數大於 2 才隔離；每 10 筆嘗試 HDBSCAN 自適應密度階梯，候選至少 25 筆；模擬操作員確認後更新全部已知基準。
- **成功標準：**程式每階段最多等待 600 tick，候選大小至少 25；未找到部署級誤發現／延遲通過線。
- **結果與限制：**九個配置均加入，需 65–265 tick；新類自身 holdout 接受率約 84.75%–100%，候選紀錄的 purity 為 1。但候選多數標記與 purity 在確認前已由真值計算；新的 holdout 也可能在先前循環到達時出現。因此它是帶標註的 oracle 流程展示，不是嚴格 arrival-only 持續學習成果。[程式][l-exp2]、[summary／各階段][r-exp2]。

#### exp3：人工劇本的漸進與突發切換

- **研究問題：**逐窗異常比例的變化，能否分辨緩慢混入與突然切換？
- **為什麼做：**單次超線容易誤報，操作員需要一段變化的描述。
- **使用資料：**T1／8000 rpm；A 劇本健康後逐步提高 7screws 比例，再切到 6／5；B 劇本健康後直接切到 4screws。seed 42，各 40 次。
- **分配：**健康 train／cal／holdout 如主線；從健康 holdout 與故障池抽樣拼接序列，不是原始連續錄製。
- **方法：**對未知指示值作 EWMA（alpha 0.08）；warmup 10、警報線 0.5；在中間帶停留不超過 12 筆判突發，否則漸進；CUSUM 另供觀察。
- **成功標準：**上述是分類規則；沒有查到事前固定的真實事件驗收率。
- **結果與限制：**兩劇本警報率皆 100%、類型各 97.5%（39／40）；平均警報延遲 A 49.8、B 7.675 tick。它證明能辨識這兩種注入方式，不證明真實磨耗與瞬間故障可照此區分；tick 不能稱真實秒。[程式][l-exp3]、[40 次產物][r-exp3]。

#### exp4：健康地圖、故障方向與嚴重度

- **研究問題：**離健康中心多遠、往哪個方向，是否對應配置關係？
- **為什麼做：**把單一分數拆成「偏離程度」與「像哪個已知方向」，方便解釋。
- **使用資料：**T1／8000 rpm、105 維、seed 42；配置族群與螺絲數排序由實驗設計指定。
- **分配：**健康建立白化基準，已知 train 建方向；部分方向門檻讀已知 holdout，嚴重度分析讀各配置完整池，並非完全獨立測試。
- **方法：**LW 健康白化、類別均值射線、餘弦相似與徑向／方向分量，另算 Spearman 排序相關。
- **成功標準：**未查到事前固定的方向 AUROC 或嚴重度相關通過線。
- **結果與限制：**半徑對指定嚴重度相關 0.8766，方向分量僅 0.1944；只用 7screws 作方向錨點時族群 AUROC 0.9968，只用 1screws 則 0.1463。方向不是天然可靠，結果高度依賴已知錨點；配置排序也不是實測損傷值。[程式][l-exp4]、[結果][r-exp4]、[幾何][l-geometry]。

#### exp5：跨馬達、跨轉速與健康漂移

- **研究問題：**來源健康基準能否直接用在另一工況？
- **為什麼做：**實際設備會有個體與轉速差異，不能只驗同工況。
- **使用資料：**九工況，來源／目標 9×9，seed 42。
- **分配：**來源健康 train／cal；同工況評估健康 holdout，異工況評估目標完整健康與故障池。
- **方法：**LW 基準直接轉移；另比較每工況、全域混合、每轉速混合建基準。
- **成功標準：**未查到事前固定的跨工況健康誤報上限。
- **結果與限制：**同工況 AUROC 為 1，72 個異工況配對平均 0.8930、最差 0.1035；同轉速跨馬達平均 0.9210、同馬達跨轉速 0.9282。但直接轉移的目標健康接受率均為零：幾乎所有目標健康都落在來源門檻外。策略比較還有切分問題：外層 holdout 用 seed+7，每工況基準卻重新從全池以 seed 建 train／cal，兩者不保證互斥。因此既有策略表不能當成乾淨、同切分的排名；T1／T2／T3 的分數差亦不能推成老化因果。[程式][l-exp5]、[結果][r-exp5]。

### 7.3 exp6–9：方法比較與健康指數

#### exp6：正式 Mahalanobis／k-NN 矩陣

- **研究問題：**排除不同切分與門檻來源後，兩種主線拒絕法是否有明顯差異？
- **為什麼做：**提供最清楚的同設定對照，而不是拿兩份不同實驗分數比較。
- **使用資料：**九工況、105 維、seed 42／123／2026、兩方法，共 54 列；初始已知僅健康，九故障配置皆未知。

#### exp8：健康指數、逐窗狀態與彙總重算

### 7.4 exp10–12：轉移、舊新比較與視覺化

#### exp10：少量目標健康資料的中心平移

- **研究問題：**用少量目標健康資料調整來源模型，是否比目標端從頭建立基準划算？
- **為什麼做：**exp5 已顯示跨工況門檻失效，需區分修好排序與修好實際接受率。
- **使用資料：**九工況的 72 個有方向來源／目標配對，seed 42；每對 direct 一組，加 10／25／50 筆的 adapted、scratch 各三組，共 504 列。
- **分配：**來源健康 train／cal；目標支持集不進剩餘評估。adapted 與 scratch 在相同 N 使用同一支持／評估資料；各 N 重新抽支持集，並非逐步嵌套。scratch 再把支持資料切 60／20／20，評估使用外部剩餘池。
- **方法：**原始特徵空間的來源／目標中位數平移，加 LW；scratch 則只用目標支持資料建立。這是工程平移法，不是完整 CORAL。
- **成功標準：**未查到事前固定的勝負幅度；觀察 AUROC、健康接受與故障偵測三者，不能只看 AUROC。
- **結果與限制：**direct AUROC 0.8930、健康接受 0；平移 N=10／25／50 的 AUROC 約 0.9992／0.9992／0.9994，健康接受卻僅 7.27%／8.77%／9.31%。scratch 對應為 65.66%／83.62%／87.90%，故障偵測皆 100%。50 筆時從頭建立比平移多接受 78.59 百分點的健康窗，說明舊模型尺度仍不適配。direct 評估全健康池，其他組排除支持集，不能當成完全相同測試集的配對改善。[程式][l-exp10]、[結果][r-exp10]。

#### exp11：Ancestor 協定對照，但 legacy 基準存在不相容

- **研究問題：**同一配置設定中，legacy 與 LW 的已知分類、未知拒絕差多少？
- **為什麼做：**把舊新流程放到同一執行器，原意是補上可量化對照。
- **使用資料：**九工況、三 seed、兩方法、兩協定，共 108 列。A 已知 `8、1、2、3、4`、未知 `5、6、7、3_14、4_146`；B 僅健康已知。
- **分配：**已知 60／20／20；legacy train 自我門檻、LW 獨立 calibration，未知只評估。這也不是原 Ancestor CNN 的完整重新訓練比較。
- **方法：**`build_ancestor_monitor` 選 legacy／LW，再由 `OpenSetMonitor.classify` 統一產生類別；另作 Wilcoxon 配對摘要。
- **成功標準：**程式註明 balanced accuracy 與 macro-F1 對 legacy 都增加至少 5 百分點；未取得獨立於測試結果的事前登錄證據。
- **結果與限制：**A 紀錄 balanced accuracy 16.67%→95.05%、macro-F1 0.1512→0.9730；B 為 50.00%→97.14%、0.4946→0.9847。但 legacy 偵測器的單一全域類別標籤是 `-1`，`classify()` 把任何負標籤轉為未知，造成所有 legacy 預測皆未知。這些巨大差值首先反映介面不相容，不能當成 LW 超越 Ancestor 的科學證據，p 值也不能補救。[實驗][l-exp11]、[分類介面][l-monitor]、[legacy 標籤][l-maha]、[保存結果][r-exp11]。

#### exp12：混淆矩陣與 t-SNE

- **研究問題：**健康誤拒、已知錯類與未知漏接在圖上如何分布？
- **為什麼做：**讓單一 accuracy 背後的錯誤可被看見。
- **使用資料：**九工況、seed 42；二元健康／未知及 exp11 A 的多類協定。
- **分配：**矩陣採健康／已知 holdout 加未知池；t-SNE 每類最多抽 200 筆完整池資料，可能包含 train，不能當獨立測試分離度。
- **方法：**混淆矩陣；train 擬合 scaler 後，把抽樣資料共同嵌入 t-SNE（perplexity 30）。
- **成功標準：**未查到事前固定的圖形分離通過線；有圖片不等於模型合格。
- **結果與限制：**LW 二元矩陣為健康 527 接受／45 拒絕，故障 26070 拒絕／0 漏接，即健康誤報 7.87%、故障偵測 100%。多類 legacy 圖沿用 exp11 負標籤問題；t-SNE 的團塊與間距不能證明新馬達可分，summary 也未保存投影座標。[程式][l-exp12]、[summary 與圖檔目錄][r-exp12]。

### 7.6 歷史實驗：在預訓練 CNN 特徵上比較 LW／OAS／MCD

- **研究問題：**小樣本、高維且相關的深層特徵，能否用既有共變異數估計改善未知拒絕？
- **為什麼做：**原始樣本共變異數的反矩陣容易受微小特徵值、離群點與訓練自我校準影響。
- **使用資料：**2026-08-06 的 18 個預訓練模型：T1 Model01–09、T3 Model19–27，三種架構 × 三轉速 × 兩馬達，深層維度 176／128／48，每配置最多 300 筆。當時未納入 Model10–18，不代表目前 D 槽或整個專案沒有 T2 模型。
- **分配：**已知 `8、1、2、3、4` 作分層 60／20／20，seed 42；未知 `5、6、7、3_14、4_146` 只評估。偵測器 scaler 只 fit known train；預訓練 CNN 原先是否見過這些 cal／test 窗，未取得完整排除證據。
- **方法：**legacy 全域共變異數、HDBSCAN inlier 與 train q95；改版逐類中心／共變異數、獨立 calibration q95，試 LW、OAS、PCA＋MCD，CNN 權重不變。
- **成功標準：**未找到獨立保存的事前數值驗收契約；依同批 18 模型平均呈現，不用事後分數倒填。

|---|---:|---:|---:|---:|
| 開集準確率 | 95.09% | 98.64% | 98.61% | 92.27% |
| balanced accuracy | 90.22% | 96.72% | 96.63% | 92.96% |
| AUROC | 0.9884 | 0.9987 | 0.9987 | 0.9752 |

- **結果與限制：**LW 在 immutable test 未知召回 59.10%、健康誤報 0.23%、AUROC 0.7859；k-NN 對應 22.38%、0%、0.7630。另在合併評分池 q95 下，legacy／LW 未知召回 27.93%／61.73%、AUROC 0.7255／0.8080，仍不能拆成單一共變異數因果。三 seed 有相同結果，不代表增加了三次獨立採集。[六法結果][r-research-detectors]、[消融結果][r-research-calibration]。

#### R2：已知配置數目、組合與開放集矩陣

- **研究問題：**健康以外逐漸增加已知故障，能否既分對已知又拒絕剩餘配置？
- **為什麼做：**健康／異常二分成功，不表示能完成多類診斷。
- **使用資料：**三馬達、三轉速、90 CSV、28910 窗；Protocol A 的 N=5 包含全部 126 個已知故障組合，另有 N=1–8 與 N=9 closed-set；Protocol B 有 30 組平衡組合與未知 validation 輪替，共 2490 格。
- **分配：**三個循環 motor fold；早期 validation／calibration 共用，且跨折 selector 有曝光依賴。不能把這批標成 fresh，後來 R3 才修正部分程序。
- **方法：**平衡 multinomial logistic regression（C=1、lbfgs、最多 1000 iteration）分類，拒絕分別用 LW Mahalanobis／k-NN（k=5）。
- **成功標準：**跑完矩陣不等於研究達標；每類測試群組不足及 validation／calibration 共用使獨立性驗收仍為 INCOMPLETE。
- **結果與限制：**A 的 N=5 已知分類約 25.74%；Mahalanobis／k-NN 的未知 AUROC 0.5278／0.5245、未知召回 15.00%／7.94%。N=1／5／8 的已知準確率約 69.35%／25.74%／18.54%，N=9 closed-set 約 16.44%。組合、類別數與機會水準都在變，不能斷言「類別增加導致固定幅度退步」，但足以否定多類配置辨識已解決。[完整結論與更正][research-final]。

#### R3：固定三馬達角色與 105／75 維比較

- **研究問題：**移除共同選模及 val／cal 共用後，結果是否改變？去掉電流／溫差是否有幫助？
- **為什麼做：**先檢查切分與表示，再談換更複雜模型。
- **使用資料：**第 6.2 節的固定 N=5，三折、seed 0／1／2；36 次評估、18 次分類器擬合、346920 筆預測紀錄，沒有增加獨立樣本數。
- **分配：**train／cal／test 按馬達隔離，selection／validation IDs 為空；只 known calibration 定門檻。歷史 test 已曝光。
- **方法：**固定 logistic classifier 與主線拒絕法；比較 105 維與三軸振動 75 維。
- **成功標準：**程序要求角色分離與來源相符；不以程序修正必須提高準確率作驗收。
- **結果與限制：**修正程序後預測差異為零；105→75 維的已知分類約 29.63%→34.15%，增加 4.52 百分點，Mahalanobis 未知召回約 15.07%→18.44%，增加 3.37 百分點，但 T1 未知召回仍為零。這是局部改善，不足以部署。[固定結果索引][research-fixed]、[研究報告][research-report]。

#### R4：分類器、表示與分類／拒絕解耦（早期 S8、C、D／P）

- **研究問題：**分類邊界、特徵表示、拒絕器各自造成多少問題？
- **為什麼做：**換 classifier 不一定改變 unknown detector，需拆開驗證。
- **使用資料：**同一固定 N=5、三馬達；75／105 維、去重 66 維、harmonic 69 維與幅值／形狀表示；S8 為較早的選模研究，不與固定後資料當獨立證據相加。
- **分配：**後續 C／D 使用固定 train／known cal／motor test；早期 S8 的跨折選模依賴另列限制。
- **方法：**logistic／LDA／SVM／樹／k-NN／PCA／NCA／RDA 等有限候選；D 將分類器與拒絕器分開接。C 保存 630 planned、624 completed、6 incomplete；D／P 81／81。
- **成功標準：**早期 C／D 沒有與下節完全相同的全套契約，不能事後宣布通過；同時檢查故障分類、健康誤報與最差馬達。
- **結果與限制：**seed 0、motor 等權下，C02（75 維 logistic＋Maha）已知 34.15%、故障 26.61%、健康總誤報 26.87%、未知召回 18.44%；D01（C17 classifier＋C02 detector）為 39.29%、30.43%、14.13%、18.44%。已知提高約 5.13 百分點、健康總誤報降低 12.74 百分點，但未知沒有改善，且 T1 未知、部分已知配置召回仍為零。這解釋了為何不能挑單欄宣布優勝。[完整表與來源][research-report]、[來源索引][l-research-index]。

#### R6：真正的 arrival-only 更新比較

- **研究問題：**只用已到達且已確認的樣本，能否學新配置並保留舊類？
- **為什麼做：**區分 exp2 完整池 oracle 與資料受限更新。
- **使用資料：**P1；三 seed、四 arrival order、五策略、budget 10／25／50／100，共 240 列，immutable test 7422 窗。
- **分配：**arrival-only 策略記錄實際可讀 IDs，`future_samples_read=false`；full-pool oracle 明確標 `is_oracle=true`。arrival order 是合成，不是實際時間。
- **方法：**完整歷史 replay、固定隨機／平衡 replay、新類-only，以及完整池 oracle；未實作完整 EWC／iCaRL，不能借用它們的成果名稱。
- **成功標準：**程式可檢查未來資料禁讀與固定 test；未找到所有場景通用的部署提升通過線。
- **結果與限制：**保存各類召回、macro-F1 與遺忘比較，沒有可支持「少量到達樣本就穩定學會全部故障」的結果；部分新類召回極低或為零。主要成果是把 oracle 優勢與到達限制分開驗證，並未解決跨馬達分類瓶頸。[240 列原結果][r-research-continual]。

#### R7：混合未知、健康污染與合成現場場景

- **研究問題：**混合陌生配置、輸入損壞、短暫尖峰與健康污染會怎樣？
- **為什麼做：**平均分數以外，還要知道錯誤在哪些操作條件出現。
- **使用資料：**既有特徵與 P1 角色；人為混合配置／插入缺值、飽和、偏移、flatline、dropout、時間缺口等測試。
- **分配：**沿既有固定 train／cal／test，場景注入不當成新獨立採集；合成時間只供規則驗證。
- **方法：**HDBSCAN 群組品質、逐窗與持續事件告警、品質旗標、0／1／5／10% 健康訓練污染。
- **成功標準：**品質規則與事件持續條件可查；未找到真實每小時誤報／現場延遲驗收依據。
- **結果與限制：**選定兩配置混合的 200 窗可成兩群，purity／ARI／NMI 皆 1；單尖峰事件有一次誤警報、連續規則為零，持續事件合成延遲為 1 個模擬秒。但污染實驗健康誤報基線已達 100%，不能宣稱抗污染可靠。這些是壓力情境，不是真實硬體成績。[場景原結果][r-research-field]。

#### R8：健康偏離與「被模型認識」分開，以及資料／同步稽核

- **研究問題：**新類加入後分數下降，到底是變健康還是變熟悉？來源驗證能確認到哪一層？
- **為什麼做：**避免把學習造成的分數改變寫成修復，並避免特徵 ID 正確就宣稱 raw 獨立。
- **使用資料：**既有池的 100 個 probes、正式來源副本與同步 fixture；沒有新真實磨損或完整生命週期資料。
- **分配：**健康錨點凍結，只有開集熟悉度更新；同步入口先以 schema／fixture 驗證，fresh gate 仍要求新來源證據。
- **方法：**分離健康偏離、未知分數、方向熟悉度；內容／ID／外層預測 verifier，以及 raw ingest／feature contract。
- **成功標準：**健康錨點不因認識新類而改變、來源 ID／SHA 相符、沒有合格來源時不得升級成 fresh；不設定虛構 RUL 通過線。
- **結果與限制：**probes 健康偏離最大變化為零；未知平均分數約 0.7177→0.5582，方向熟悉度 0→0.9989。它顯示「認識」可變而健康基準不變，不證明實體修復。同步／來源稽核已有工程入口，但原始 session、重疊與清理同步仍 UNKNOWN，沒有合格新 raw 或生命週期資料完成 final 驗證。[分數分離原結果][r-research-separation]、[同步證據 registry][r-research-sync]、[獨立性稽核][research-independence]。

## 9. 目前不成功，或還不能回答的事

### 9.1 跨工況與多類配置辨識仍是主要弱點

同工況 healthy-only 的好分數，來自每個工況各自有健康參考。直接搬來源基準會把目標健康也拒絕；用中心平移可改善排序，仍未修好門檻。固定跨馬達的多類研究還有已知配置混淆、未知召回不足及部分工況健康全誤報。這些現象共同指出「資料表示與校準跨個體失配」值得優先處理，但現有資料不能把原因指定為老化、負載或感測器安裝。[exp5][r-exp5]、[exp10][r-exp10]、[跨馬達失敗分析][research-report]。

已知分類器與拒絕器也會互相限制：分類器換得較好，沿用原拒絕器時 unknown recall 可能完全不變；為了提高 unknown recall 放寬拒絕，又可能犧牲大量健康窗。D01 與後續 J／K／M 批次保留了這些取捨，沒有候選同時通過整套保護條件。[原研究報告][research-report]。

### 9.2 更新後分數下降，不表示馬達被修好了

exp2 與目前 Web 的確認更新讀取完整標記配置池，包括尚未到達的樣本；新切出的 holdout 也可能在先前到達序列出現。這種 oracle 可展示整個功能流程，不能當成只用現場累積樣本學會新類的證據。arrival-only 比較必須另外限制可用 IDs、保留固定測試集，並量化舊類遺忘與新類召回。[exp2][l-exp2]、[受限更新研究][r-research-continual]。

「原本陌生，現在認得」只改變模型的知識，不改變設備的螺絲與訊號。主 Web 顯示的 `1/score×100` 健康度、exp8 的校準指數、PolarMap 半徑與方向是不同量尺；它們都沒有損傷真值。學新故障後開集分數下降，不能寫成健康恢復。`prediction_confidence` 是距離拒絕線的代理值，不是經校準的機率。[主展示][l-live]、[健康模組讀法][l-health-guide]、[分數分離對照][r-research-separation]。

### 9.3 尚缺獨立、同步與真實時間的證據

同配置的窗隨機切分，可能共享錄製環境、相鄰訊號與全池清理統計。跨馬達雖比逐窗洗牌嚴格，仍只有三顆個體，歷史 test 也已反覆使用。換 seed、換檔名或多產生幾百萬筆預測，不會產生新測試設備。所有相關結果都應保留探索性標記。[資料獨立性][research-independence]、[來源更正][research-provenance]。

CSV 抽樣劇本沒有真實時間鏈，不能換算現場每小時誤報與實體故障延遲；沒有從健康到失效的連續真值，不能訓練／驗收 RUL。exp8 明確輸出 `estimated_rul=None`、`rul_available=False`。Ancestor 的 T1／T2／T3 人工 HI 區間也不能拿來補足真實退化標籤。[健康 schema][l-health-schema]、[Ancestor HI notebook][a-hi]。

### 9.4 對照基準與工程留存仍有缺口

exp11／12 的 legacy 負標籤缺陷、exp5 策略切分不一致，以及 exp8 彙總末位差異，都已在第 7 節揭露；本次任務只寫報告，未修改它們或回寫更好成績。後續若修正，必須以新的程式版本與新輸出驗證，保留原始失敗產物。

環境 sidecar 只涵蓋 `setup_run()` 入口；健康 benchmark／matrix／monitor 尚未全部統一。部分歷史產物缺完整環境或為 dirty 工作樹。正式轉換 manifest 仍含私人絕對路徑，公開前不能直接貼出；秒級輸出目錄亦不能保證併發執行不撞名。這些影響重現與分享，不改寫成「已全面追溯」。[環境操作契約][l-runtime-policy]、[日誌 writer][l-logger]、[資料操作契約][l-formal-guide]。

## 10. 怎麼操作與示範

這裡只走一條故事：**建立健康基準 → 播放健康 → 輸入陌生來源 → 等候選 → 模擬確認 → 看它成為已知。** 所有命令在選定的 Lineage checkout 根目錄執行；以下是依目前 CLI 與 UI 核對的操作方式，本次沒有另啟動硬體或重新訓練正式資料。完整文件見 [環境操作][l-runtime-policy]、[逐步導覽][l-guide-readme] 與 [實驗手冊][l-handbooks]。

### 10.1 環境與資料前提

主線正式要求 CPython 3.10.x 與 uv，不需要 TensorFlow／GPU；八項直接依賴在 `pyproject.toml` 訂死，完整依賴樹由 `uv.lock` 鎖定。目前為 NumPy 2.2.6、pandas 2.3.3、Matplotlib 3.10.9、SciPy 1.15.3、scikit-learn 1.7.2、hdbscan 0.8.44、loguru 0.7.3、Tornado 6.5.10。[依賴宣告][l-env]、[lock][l-lock]。

Windows PowerShell 7 的最小操作如下；`C:/path/to/python3.10.exe` 必須換成實際安裝路徑，`.venv310` 必須是不存在的新目錄，不能刪除既有環境來配合範例。

```powershell
./build_uv.ps1 -Python 'C:/path/to/python3.10.exe' -VenvDir '.venv310'
uv pip check --python .venv310/Scripts/python.exe
uv run --no-project --no-sync --python .venv310/Scripts/python.exe python -m experiments.exp1_cold_start --help
```

安裝入口使用 `uv sync --locked`，不應回退成未鎖版的 pip／venv 安裝。Linux 可用 `./build_uv.sh --python python3.10 --venv .venv310`，後面 executable 改 `.venv310/bin/python`。legacy TensorFlow 清單不受同一 lock 管理，也不在本輪正式相容驗證範圍。[安裝實作][l-build-windows]、[最新操作政策][l-runtime-policy]。

GitHub checkout 不附正式大資料。需先從組內唯讀來源提供 clean CSV，並保持第 6 節的目錄與 105 維契約；以下例子假設已放在 `data`。至少要有選定工況的健康配置；要示範新類還需另一配置。九工況正式矩陣要求完整九工況，單頁可開不代表矩陣資料齊全。若只有 archive，先閱讀 [物化契約][l-formal-guide]，另指定新的目的資料版本；不要對原正式 `data` 使用 `--force`。本次未重建任何資料。

### 10.3 建議展示：獨立逐步導覽

```powershell
uv run --no-project --no-sync --python .venv310/Scripts/python.exe python -m web.guide --data-root data --port 8601 --seed 42 --rate 4
```

開啟 `http://127.0.0.1:8601`。目前頁名是「先認識健康，再處理未知」；啟動時尚未擬合，須明確建立基準。[導覽伺服器][l-guide]、[實際 HTML][l-guide-html]。

1. 選「開始冷啟動監測」，選馬達／轉速，按「確認所選資料」。先看工況、105 維、可用筆數及 seed；不足時停在這裡。
2. 按「建立健康基準」，再按「開始／繼續」，觀察健康來源的分數與偶發超線。每秒 4 筆只是播放速度。
3. 切「觀看未知故障學習」，在「訊號來源」選另一來源，按「輸入所選來源」。示範模式使用匿名來源；解答仍在後端快取，不是完全無標籤採集。
4. 看分數超過 1 被拒絕、超過 2 進隔離；等待候選出現。至少 25 筆不保證成群；不成群時看隔離筆數與紀錄，不宣稱模型卡住或一定會發現。
5. 候選出現才按「模擬操作員確認」。既有已知候選會被退回；新類會讀完整配置池重擬合。確認後再次輸入同來源，觀察「認出」與「健康」的差別。
6. 按「暫停」；切「研究模式」可查看來源 SHA、split IDs、門檻與七問摘要，模式切換不重訓。若要比較「漸進劇本 A／突發劇本 B」，各自先重設健康基準，避免把已學會狀態帶進另一場。

導覽寫入 `logs/web_guide/{時間}.log` 與 `output/web_guide/{時間}/`，包含環境及 session 樣本／模型快照。按暫停只停播放；終端 `Ctrl+C` 才結束伺服器。重連或候選 ID 過期時，先等畫面同步，不重複按確認。這條示範的歷史逐筆一致性證據是第 7.5 節，不是本次另跑一輪。[導覽狀態與控制][l-guide]、[回放紀錄][l-live]。

## 11. 結論與下一步

Ancestor 已提供資料處理、特徵工程、CNN／遷移、未知偵測與分群研究基礎。Lineage 可明確交代的貢獻，是把健康冷啟動、逐類距離與校準、未知候選確認、更新、趨勢、健康解釋及 Web／CLI 整理成可比較、可追查的研究系統；其中採用的 LW、HDBSCAN、k-NN 等方法有公開來源，不是本專題發明。

最可信的實驗結論是：**在每個工況都有自己的健康基準時，現有九種非健康配置容易被拒絕；跨馬達多類配置辨識與門檻轉移仍沒有解決。** 歷史深層特徵流程改善可保留，但不能從那批高準確率跨推到新馬達、真實磨損、物理故障原因或 RUL。

下一步依證據排序，不預設繼續加模型：

1. **先修正比較的有效性。** 另開程式修正工作，檢查 exp11／12 的 legacy label 語意與分類能力，以及 exp5 策略的共同互斥 split。先固定公平比較與數值驗收，再產生新結果；原結果保留。這比再報一個巨大提升重要。
2. **先補來源與研究問題邊界。** 明確把標籤稱為配置，盤清可用 motor／recording 群組、窗起訖、清理與同步資訊；取得不到的維持 UNKNOWN。嚴格 schema／內容 SHA 的候選 PR 通過不等於取得新獨立資料。
3. **預先固定少量跨馬達對照。** 沿用 train／known calibration／test 分離，分層看每顆馬達、每轉速的健康誤報、故障分類與未知召回；已曝光資料只做探索。若要宣稱泛化，需另保留來源可驗證、未參與選模的新測試群組。
4. **把更新驗收改成到達受限，健康錨點另保留。** 使用已確認的到達 IDs、固定 test 與明確 replay budget，比較新類召回、舊類遺忘及健康誤報；與 full-pool oracle 分列。沒有連續失效真值前，不啟動 RUL 成果宣稱。

這些是後續待授權的研究／修正方向。本報告交付後停止本次整理，不自行修改演算法、啟動新批次或合併 PR。
