# 實驗說明手冊（寫給第一次接觸的讀者）

這份文件用最白話的方式，解釋本專題**每一個實驗在做什麼、為什麼這樣設計、
預期看到什麼、實際看到什麼**。讀完不需要任何機器學習背景。
（想看精簡版與完整數據表 → [專案 README](../README.md)；想自己動手跑 → 每節最後都有指令。）

## 0. 這個專案在做什麼？（一個比喻）

想像一位剛畢業的醫生，被派到一個從來沒有人生過病的村莊：

> 他**只看過健康的人**。有一天村民開始生病——他沒看過任何病，
> 但他可以說「這個人跟我認識的健康人**不一樣**」（偵測異常）；
> 把症狀相似的病人分在同一群（分群）；請資深顧問確認這是什麼病（操作員確認）；
> 然後把這種病記進他的醫學筆記（量尺擴張）。下次再遇到，他就直接認得了。

本專題就是把這位醫生做成一套馬達故障監測系統：

1. **一開始只認識「健康」**（冷啟動——因為新設備剛裝機時根本還沒壞過，收不到故障資料）
2. 故障出現時**知道自己不認識它**（未知偵測）
3. 把不認識的樣本**分群、命名、學起來**（持續學習）
4. 順便判斷故障是**慢慢惡化**（磨損）還是**突然發生**（外力撞擊）

六個實驗就是分別驗證這套系統的每一種能力。

## 1. 讀懂實驗前，先認識五個名詞

| 名詞 | 白話解釋 |
|---|---|
| **樣本** | 馬達運轉 1 秒的感測紀錄（振動、電流、溫度差），濃縮成 105 個數字的「體檢報告」 |
| **健康基準** | 用一堆健康樣本算出「健康長什麼樣子」的統計模型——像健檢的正常值範圍，但是 105 個指標一起看 |
| **開集分數** | 一筆樣本「離健康多遠」的數字。**> 1 = 超出健康範圍 = 判定未知**。健康樣本通常在 0.8 左右，故障樣本動輒 30~100 |
| **隔離區** | 被判「未知」的樣本先關進來的待查名單，湊滿 25 筆就嘗試分群看它們是不是同一種新故障 |
| **量尺** | 系統目前認識的類別清單。一開始只有「健康」一格，每學會一種故障就多一格 |

### 資料哪裡來？

沿用學長論文的實驗資料：拿真實馬達，**故意拆固定螺絲來模擬故障**——
8 顆全鎖 = 健康；拆到剩 7、6、…、1 顆 = 越來越嚴重的鬆動；
另有兩種「不規則拆法」（3_14、4_146）代表跟均勻鬆動不同型的故障。
共 10 種配置 × 9 組工況（3 個馬達壽命期 × 3 種轉速），每組約 3000 筆樣本。

**重點：故障資料只拿來「考」系統，絕不拿來「教」系統**（除了被操作員確認的那一刻）。
就像考試不能先看考題——這是所有實驗共同的鐵則。

### 共同的實驗設定

- 健康資料切三份：60% 訓練（建立基準）、20% 校準（決定「多遠算超過」的門檻）、
  20% 保留（考試用，模型從沒看過）
- 所有隨機性固定種子（seed=42）——任何人重跑都會得到一模一樣的數字

## 2. 實驗一：冷啟動偵測能力（exp1_cold_start）

> 程式：`src/experiments/exp1_cold_start.py`。技術報告：[experiments/exp1_cold_start.md](experiments/exp1_cold_start.md)。

### 想回答的問題
> 只看過健康的系統，能不能把「從來沒見過的九種故障」通通抓出來？

### 設計理念
這是整套系統的地基。如果連「有沒有異常」都判不準，後面的分群、學習都免談。
方法刻意選**不需要任何故障資料**的：把健康樣本的分布建成統計模型
（Mahalanobis–Taguchi 式的做法，工業界用了幾十年的老招，配上現代的
Ledoit–Wolf 收縮讓它在 105 維也穩定），新樣本算「離健康分布多遠」。

### 實驗方法（一步一步）
1. 只用 8screws（健康）的訓練份建立健康基準
2. 用健康的校準份決定門檻：校準樣本距離的第 95 百分位 = 分數 1.0
3. 考試：把健康保留份（該判正常）與九種故障全部樣本（該判未知）丟進去
4. 記分：故障被判未知的比例（偵測率）、健康被誤判的比例（誤報率）、AUROC
   （0.5 = 亂猜、1.0 = 完美分離）

### 預期
故障偵測率越高越好、健康誤報率理論上約 5%（門檻取 95 百分位的天生代價）。

### 實際結果（T1/8000rpm）
**九種故障偵測率全部 100%、AUROC 全部 1.0**；健康誤報 10.9%
（比理論 5% 高，因為校準樣本只有 62 筆——樣本少、門檻估不準，是誠實記載的限制）。
另一個有趣觀察：分數大致隨鬆動嚴重度上升（7 顆 → 1 顆），代表「距離」隱含嚴重度資訊
（實驗四會深入）。

```bash
venv/bin/python -m experiments.exp1_cold_start --motor T1 --rpm 8000rpm
```

## 3. 實驗二：量尺擴張（exp2_scale_growth）

> 程式：`src/experiments/exp2_scale_growth.py`。技術報告：[experiments/exp2_scale_growth.md](experiments/exp2_scale_growth.md)。

### 想回答的問題
> 故障一種一種出現時，系統能不能自動「發現 → 命名 → 學會」，而且不忘記舊的？

### 設計理念
偵測到未知只是第一步，真正的價值是**把未知變已知**。設計成一條流水線：
未知樣本 → 隔離區 → 湊滿 25 筆用 HDBSCAN 分群（一種會自己判斷「這些點算不算
一群」的演算法）→ 形成候選 → **操作員確認**（人在迴圈：系統提名、人拍板，
避免自己教自己教錯）→ 納入量尺、整組重新擬合。

兩個關鍵防呆設計（都是實測踩坑後加的）：
- **隔離線**：健康樣本天生有 ~10% 會些微超線（分數 1.01~1.08），這些「邊界誤報」
  累積久了會自己聚成一群假故障。實測發現真故障分數都 ≥ 10，所以規定
  **分數 > 2 才進隔離區**——誤報進不來、故障全進得來。
- **自適應分群**：嚴重鬆動的樣本在特徵空間比較「散」，固定參數的 HDBSCAN
  要累積 200~600 筆才聚得成群（甚至失敗）。改成隔離區越大、分群的密度要求
  自動放寬——但「一群至少 25 筆」的品質門檻不變。

### 實驗方法
把九種故障**由輕到重依序注入**，每種記錄：發現花了幾筆（發現延遲）、
分群純度（群裡有沒有混到別的故障）、學會後認不認得自己（自類準確率）、
學新的會不會忘舊的（健康保持率）。

### 預期
每種故障都能被發現且純度高；已知類別越多，各類的判定空間越擠，準確率會緩降。

### 實際結果（T1/8000rpm）
**十種配置全部成功發現與學會、所有分群純度 100%**（從來沒把兩種故障混成一群）；
發現延遲 65~265 筆；自類準確率從 100% 緩降到 ~85%（量尺擴張的代價，如預期）；
健康保持率始終 ≥ 90%。

```bash
venv/bin/python -m experiments.exp2_scale_growth
```

## 4. 實驗三：漸進 vs 突發判別（exp3_trend）

> 程式：`src/experiments/exp3_trend.py`、`src/core/trend.py`。技術報告：[experiments/exp3_trend.md](experiments/exp3_trend.md)。

### 想回答的問題
> 能不能從「異常出現的節奏」分辨：這是慢慢磨壞的，還是突然被撞壞的？

### 設計理念
同樣是生病，「越來越常咳嗽」和「突然骨折」的處置完全不同。馬達也是：
螺絲慢慢鬆（磨損 → 排程保養）vs 異物撞擊（突發 → 立刻停機檢查）。
判別的線索不在單一樣本，而在**時間序列的形狀**：把每秒「是否異常」
用 EWMA（指數加權平均，一種會記得最近趨勢的平滑器）算成「異常密度」——
慢性惡化的密度會**慢慢爬**、在中間值徘徊很久；突發事件**直接跳上去**。

### 實驗方法
1. 造兩種劇本：**劇本 A（漸進）**——健康 → 25% 混入輕度故障 → 70% → 更嚴重
   （模擬早期間歇性症狀）；**劇本 B（突發）**——健康 → 下一秒直接全是中度故障
2. 異常密度超過 0.5 觸發警報；回看警報前它在「中間帶」（0.2~0.5）停留了幾筆——
   停留短（≤ 12 筆）判突發、停留長判漸進
3. 每種劇本隨機重複 40 次，統計判別正確率

### 預期
兩種劇本都能 100% 觸發警報，且大部分判別正確。

### 實際結果（T1/8000rpm，40 次重複）
警報率兩者皆 100%；判別正確率**各 98%**；突發平均 7.7 筆就警報、漸進 49.8 筆
（因為它本來就是慢慢來的）。兩種劇本的「中間帶停留時間」分布（5~13 筆 vs 12~60 筆）
只在交界處少量重疊——98% 反映的是真實的物理差異，不是調參調出來的。

```bash
venv/bin/python -m experiments.exp3_trend --trials 40
```

## 5. 實驗四：極座標健康地圖（exp4_polar_map）

> 程式：`src/experiments/exp4_polar_map.py`、`src/core/geometry.py`。技術報告：[experiments/exp4_polar_map.md](experiments/exp4_polar_map.md)。

### 想回答的問題
> 異常不只「有多遠」，還有「往哪個方向」。新異常出現時，能不能自動判斷它是
> 「已知故障的更嚴重版本」還是「一種全新的故障」？嚴重度能不能直接從距離讀出來？

### 設計理念
把特徵空間想成一張地圖：**健康是市中心**，每種故障是從市中心往外的**一條路**。
同一種故障惡化 = 沿同一條路越走越遠；全新的故障 = 從市中心往**另一個方向**開出新路。
數學上：在「白化」過的空間裡（把健康分布捏成標準圓球，方向比較才公平），
算每個異常樣本與已知故障方向的夾角餘弦（cos）——**cos 高 = 熟悉的方向、
cos 低 = 新方向**；離市中心的距離 = 嚴重度。

### 實驗方法
- (a) 把十種配置全學會，量每兩條「路」之間的夾角——驗證地圖假設本身
- (b) 只讓系統認識一種故障，注入其他故障，看「方向熟悉度」能不能把
  「同家族的更嚴重版本」和「真正的新型故障（4_146）」分開（AUROC）
- (c) 只給兩端錨點（最輕 7screws、最重 1screws），對中間等級算嚴重度，
  看排序對不對（Spearman ρ，1.0 = 完全照嚴重度排）

### 預期
均勻鬆動們應該大致同一條路、複合故障是別條路；嚴重度應該能粗略排序。

### 實際結果（T1/8000rpm）——三個誠實的發現
1. **地圖假設部分成立**：中段均勻鬆動（6~2 顆）確實擠在同一束路上（cos 0.92）、
   4_146 明確是另一條路（cos 0.49）；但最輕與最重兩端會偏離主束、
   3_14 在方向上其實仍像「鬆動家族」（0.76）——世界比比喻複雜，且可以量化。
2. **錨點效應（本實驗最重要的發現）**：用「最輕故障」當羅盤，分辨
   「家族惡化 vs 新型故障」的 AUROC 高達 **0.997**（中度錨點 1.000）；
   但用「最嚴重故障」當羅盤會**整個反過來（0.146）**——從極端看世界會誤判。
   幸運的是：真實部署最先遇到的正是輕度故障，輕度錨點恰好是最準的。
3. **嚴重度可以粗排、難細排**：純距離的排序相關 ρ=0.877（輕重兩端分得很清楚），
   但中段有物理性的距離倒置（5 顆比 4 顆遠），細粒度排序是誠實記載的限制。

Web 展示上這變成一張即時的「極座標健康地圖」：圓心是健康、✕ 是已知故障路的
盡頭、每筆樣本依方向熟悉度落點——觀眾一眼看懂「往熟路走」還是「開新路」。

```bash
venv/bin/python -m experiments.exp4_polar_map --motor T1 --rpm 8000rpm
```

## 6. 實驗五：跨工況冷啟動泛化（exp5_cross_condition）

> 程式：`src/experiments/exp5_cross_condition.py`。技術報告：[experiments/exp5_cross_condition.md](experiments/exp5_cross_condition.md)。

### 想回答的問題
> 在 A 條件（某顆馬達、某轉速）建的健康基準，直接拿去 B 條件用，行不行？
> 老化本身會造成多大的「漂移」？

### 設計理念
真實工廠不會只有一台機器、一種轉速。如果每換一個條件就要重新收資料，
部署成本會爆炸；但如果亂共用基準，誤報會爆炸。這個實驗把「能不能共用」
變成一張 9×9 的成績單（3 壽命期 × 3 轉速互相測），並比較三種部署策略。

### 實驗方法
- (a) 9×9 遷移矩陣：每組工況建基準 → 測全部 9 組的健康接受率/故障偵測率/AUROC
- (b) 三種策略：逐工況各建基準 vs 九組健康混在一起建一個 vs 同轉速三顆混建
- (c) 老化漂移：用 T1（新機）的基準去看 T2/T3（老機）的「健康」資料

### 預期
自身工況最準；跨條件會掉；老化會造成可觀漂移。

### 實際結果
- (a) 自身 AUROC 全部 1.0；跨工況平均掉到 0.893、**最糟的組合只剩 0.10**——
  基準不能亂搬。
- (b) **逐工況基準最優**（健康接受 97.4%、故障偵測 100%），混合策略兩者皆輸——
  用數據支持了本系統「每個工況各自冷啟動」的架構選擇。
- (c) 最戲劇性：T1 基準看 T2/T3 的「健康」資料，**100% 被判為未知**
  （分數中位 14~86，遠超門檻 1.0）。白話：**老機器的健康 ≠ 新機器的健康**。
  誠實註記：T1/T2/T3 是三顆不同的馬達個體，這個位移是「個體差異 + 老化」的
  疊加，本資料無法把兩者拆開——但結論不變：健康基準必須**逐機台**建立，
  而這正是冷啟動方法的主場（每台機器裝機時自己收健康資料就好）。

```bash
venv/bin/python -m experiments.exp5_cross_condition
```

## 7. 實驗六：開集偵測方法基準比較（exp6_osr_benchmark）

> 程式：`src/experiments/exp6_osr_benchmark.py`；正式版 `src/experiments/exp6_formal_benchmark.py`、`exp6_matrix.py`、`aggregate_exp6.py`。技術報告：[experiments/exp6_osr_benchmark.md](experiments/exp6_osr_benchmark.md)。

### 想回答的問題
> 主線採用的「Ledoit–Wolf 馬氏距離」是不是合理選擇？換別的方法會不會更好？

### 設計理念
同一場考試，讓七個「學生」一起考：主線方法、論文版的舊校準法（對照組）、
以及五種經典異常偵測法（One-Class SVM、Isolation Forest、LOF、kNN 距離、
PCA 重建誤差）。所有方法用**同一套資料切分、同一套校準哲學**（校準集第 95
百分位 = 門檻），比較才公平。9 組資料集各考一次，取平均。

### 預期
方法之間應該有高下之分，主線方法希望名列前茅。

### 實際結果——一個反直覺但重要的結論
**七種方法的 AUROC 全部 1.0000**：在這份 105 維特徵上，健康與故障分得太開，
「用哪種距離」根本不是瓶頸。真正的差異在**校準品質**（健康誤報率）：
kNN 6.0% 最低、主線 LW 馬氏 7.1% 居中、**論文版 legacy 校準崩潰到 83.1%**
——它用訓練資料自己的距離定門檻，在高維+單類+小樣本下嚴重高估自己
（在論文原本五類、資料更多的設定下沒事，但冷啟動情境會爆炸）。

三個帶回家的結論：① 特徵工程（105 維）才是這個題目的英雄，偵測器選擇是配角；
② **獨立校準集是冷啟動的生死線**，不是可有可無的細節；③ 主線續用 LW 馬氏合理
——誤報與最佳者相差 1 個百分點，卻換得參數化模型才有的能力
（實驗四的幾何地圖、逐類擴張、可解釋性），kNN 等無參數方法給不了。

```bash
venv/bin/python -m experiments.exp6_osr_benchmark
```

## 8. 實驗七：單工況 Mahalanobis vs k-NN 對照（compare_openset）

> 程式：`src/experiments/compare_openset.py`。技術報告：[experiments/exp7_compare_openset.md](experiments/exp7_compare_openset.md)。

### 想回答的問題
> 在同一個工況、同一份資料切分下，把主線的馬氏距離換成 k-NN 距離，結果會差多少？

### 設計理念
實驗六的七方法比較用的是 `src/core/detectors.py` 那套偵測器。這支直接用主線監測器
`OpenSetMonitor`，只切換 `--openset-method`，其他設定（切分、校準 95 百分位、
`score > 1` 判未知）都不動，所以差異只來自距離本身。它是實驗六正式版
（9 工況 × 3 seed）的單工況前身，適合在一個工況上快速看圖。

### 實驗方法與結果
對 `--motor` / `--rpm` 指定的一個工況，兩種方法各擬合一次，算 AUROC、AUPR、
FPR@TPR95、未知 F1 與健康誤報率，畫成並排長條圖。本實驗沒有被指定為正式結論的
彙總檔，九工況的數字以實驗六正式矩陣為準。

```bash
venv/bin/python -m experiments.compare_openset --motor T1 --rpm 8000rpm
```

## 9. 實驗八：相對健康指數與健康監測（health_index_*、health_monitor）

> 程式：`src/experiments/health_index_benchmark.py`、`health_index_matrix.py`、`health_monitor.py`，邏輯在 `src/experiments/health/` 套件。技術報告：[exp8_health_index_benchmark](experiments/exp8_health_index_benchmark.md)、[exp8_health_index_matrix](experiments/exp8_health_index_matrix.md)、[exp8_health_monitor](experiments/exp8_health_monitor.md)；流程總覽 [exp8_health_monitoring_workflow.md](exp8_health_monitoring_workflow.md)。

### 想回答的問題
> 能不能把「開集分數」換成 0～1 的健康度，讓人看得懂「這顆馬達離健康多遠」？

### 設計理念
只用 `8screws` 的校準資料定刻度：校準分數第 10 百分位算健康 1.0，第 95 百分位算 0.0，
中間線性換算。再依健康度分成 healthy / early_warning / degraded / critical 四段。
現有資料沒有實體馬達編號、時間戳或真實損傷標記，所以這是**相對**健康度，
不能說成損壞百分比或剩餘壽命。

### 實際結果
9 工況 × 3 seed × 2 方法共 54 列：已知健康與未知故障的健康度平均差 0.58（Mahalanobis）
與 0.60（k-NN），AUROC 都是 1.0。所有未知故障的健康度都貼在 0.0，表示分得開，
但還排不出故障輕重。結果檔在 `reports/exp8_health_index_results/`。

```bash
venv/bin/python -m experiments.health_index_matrix --data-root data/formal_local --seed 42 --seed 123 --seed 2026 --method mahalanobis --method knn
```

## 11. 常見問題（FAQ）

**Q：為什麼健康有 ~10% 誤報、認出率不是 100%？**
門檻取校準distances的第 95 百分位，代表天生就允許 ~5% 的已知樣本落在線外；
校準樣本只有 62 筆時，這個 5% 估不準、實際變 ~10%。是統計性質，不是 bug。

**Q：為什麼候選新故障曾經顯示「Healthy」？**
上一題的邊界誤報累積自聚成群造成的歷史問題——現已用「隔離線 > 2 才進隔離區」
從源頭解決，並保留「操作員退回」當第二道保險（見實驗二的防呆設計）。

**Q：操作員確認是不是作弊？**
不是。偵測、分群全程不用任何標籤；標籤只在「確認」那一刻揭示——
對應真實世界「系統提名、維修技師拍板」的人機協作，也避免系統自己教自己教錯
（自我強化偏誤）。

**Q：這些數字換一台電腦重跑會一樣嗎？**
會。所有隨機性固定 seed=42，同指令同數字；每次執行的日誌與輸出都在
`logs/` 與 `output/` 留檔。
